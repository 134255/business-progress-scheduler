# Task 7 实施报告：审核投票、驳回返工与自动流转

日期：2026-08-11（Asia/Shanghai）

## 结果

已完成 Task 7 的本地实现与自动化验证：

- 新增 `submitReviewVote({ actor, input })` 服务入口。输入严格固定为审核轮次编号、期望轮次版本、`approve/reject` 决策、意见和请求键；驳回原因必填，原始请求键不进入仓储或持久数据。
- 投票编号由审核轮次和审核人账号编号确定性生成；投票只保存请求摘要与输入摘要。同一审核人同票同输入重试幂等，不同内容按改票冲突处理。
- 投票最终事务按活动账号、活动业务线、当前节点、活动审核轮次的固定顺序重新读取，先严格校验当前成员与审核人关系、处理人/审核人分离、审核人快照一致、节点与轮次双向锁、处理/审核轮次编号及期望版本，再读取或解释既有投票。
- 或签由首个有效赞成票结束本轮并只推进一次；会签以审核轮次锁定的审核人快照计数，只有全部有效赞成才推进；任一模式下有效驳回立即结束本轮并进入返工。
- 驳回保留审核轮次及旧反馈/字段/凭证历史，增加节点 `processingRoundNumber`，清除活动审核锁，继承提交审核时保存的剩余处理工作分钟并计算新的处理截止时间。
- 审核通过会把当前节点置为已完成；非末节点自动激活下一节点并计算处理截止时间，同时更新业务线当前节点和进度。末节点通过后完成并冻结业务线，在业务线建立统一的 60 个自然日凭证保留期限，供既有清理工作器处理整条普通业务线的凭证。
- 日历缺失不阻断驳回返工或下一节点激活，只把处理截止状态设为 `pending_calendar`、截止时间置空，并用确定性编号写入不含业务字段正文的管理员告警。
- 投票、审核审计和结果通知都使用确定性编号；并发通过/通过及通过/驳回只能提交一个确定终态和一组副作用。审计与通知不保存反馈字段正文、凭证内容或驳回意见。
- fake CloudBase 数据库从全局串行事务升级为快照式乐观事务：回调可真实重叠，提交阶段检测版本冲突并重跑，记录重叠数、冲突数和重试数。原有挑战消费测试同步改为验证“事务回调允许重试，但事务写只提交一次”。
- 两轮独立代码审查发现的重要边界均已修复。最终投票响应丢失后的重试现在仍先重读并校验活动账号、当前审核关系、业务、节点、轮次与锁版本，再核对确定性投票摘要后返回。终态轮次固化最终锁版本、节点版本、轮次版本、审核模式、处理轮次和审核轮次；重试只接受原终态精确版本，或该轮待补算处理段明确解决后节点与轮次各提升一次的唯一版本链，任意抬高版本、降低锁版本或篡改轮次语义均失败关闭。
- 当处理时间仍为 `pending_calendar` 就立即通过或驳回时，旧处理段边界绑定在不可变审核轮次上，而不再依赖节点即时状态。`calendarSync` 使用独立持久游标有界扫描 `processingCarryoverStatus: pending` 的历史轮次，所以驳回后再次提交审核、再次投票或通过后下游继续推进都不会覆盖或隐藏旧处理段。直接返工补算使用 3 次读取和 2 次写入；再次待审核时最多 4 次读取和 3 次写入，同时用差值修正节点累计值及活动轮次累计值和双向锁；业务已推进时只修正历史与累计值，不会回滚流转。日历仍缺失时保留待补算状态并维持确定性安全告警。

本任务没有接入 `businessApi/index.js` 路由，也没有修改小程序页面；统一 API 路由、审核待办和审核页面属于 Task 8。

## 并发、事务预算与安全自审

- 并发测试断言 `maxActiveCallbacks >= 2`，并观测 `conflicts >= 1` 与 `retries >= 1`；不是用串行 `Promise` 模拟并发。
- 或签通过/通过的最终状态为审核轮通过、当前节点完成、下一节点唯一激活；只存在 1 张有效投票、1 条结果通知和 1 条投票审计。
- 会签逐票更新轮次聚合计数；聚合计数必须是安全整数，满足赞成数不超过票数、票数不超过严格审核人快照人数。损坏计数在幂等早返回前也会失败关闭。
- 通过/驳回竞争依赖乐观冲突重试重新读取当前状态，最终只能留下通过或驳回之一；不会同时激活下一节点和返工。
- 每次事务尝试的操作数都有 `<= 100` 自动断言；投票不在事务内查询全部投票，而使用审核轮次上的安全聚合计数，因此事务规模不随审核人数增长。
- 历史处理段补算使用独立 `calendar-review-carryover-cursor`；40 条失效轮次后的有效轮次可在有限后续调用中到达，游标安全回绕，损坏游标失败关闭。部署手册已列入 `node_review_rounds(processingCarryoverStatus ASC, _id ASC)` 必需组合索引、游标结构与触发器前置条件。
- 账号停用、审核人移除、业务冻结、业务当前节点变化、节点或轮次锁版本变化均在读取既有投票前拒绝，不把幂等结果当作授权旁路或存在性探针。
- 请求键只传递和保存 SHA-256 摘要；通知与审计只保留必要编号、动作、决策和状态，不保存业务字段正文、凭证内容或审核意见。
- 所有最终状态和副作用在同一事务中写入；事务失败或冲突尝试不会把局部状态提交到 fake CloudBase。

## 正式复审修复轮次 1

### 修复结果

- API 输入继续使用 `approve/reject`，持久化投票、轮次最终结论和审计统一使用 `approved/rejected`。幂等比较先做规范化，旧持久语义不会被误判为新语义的同票重试。
- 投票保存事务内重新读取的活动审核人显示名快照；只读取自有数据属性，显示名非法时只回退到合法用户名，访问器、继承值或两者损坏时失败关闭。客户端不能提交显示名，投票仍保留内部审核人账号编号且不保存敏感字段。
- 每个终态投票使用 Task 4 工作时间服务结算 `reviewStartedAt` 到 `decidedAt` 的工作分钟，保存已用、剩余、逾期和日历版本。日历缺失不阻断通过或驳回，而是在终态轮次保存独立、不可变的审核时长补算边界，并写一条确定性脱敏管理员告警。
- `calendarSync` 新增独立 `calendar-review-timing-carryover-cursor`，每批总候选仍不超过 40。处理时长持续满批时仍至少为审核时长保留一个进度名额，并发游标认领只签发一批，认领后工作器崩溃也会在游标回绕后重取。审核时长补算可在返工、多轮审核、下游推进和末节点完成后到达，只修改轮次与节点时序元数据，不重新流转或覆盖业务字段。
- 候选读取、事务写回和缺日历告警都会重新校验审核时长补算边界严格等于终态轮次的 `reviewStartedAt/decidedAt`，总时限严格等于审核 SLA，pending 状态的已用、剩余、逾期和日历版本算术完全一致；损坏快照失败关闭。
- 同一终态轮次可同时保留处理时长和审核时长两类补算；终态幂等严格接受零、一或两类已声明补算各自带来的精确节点/轮次版本提升，并拒绝单边锁、任意抬高版本、状态标志或审核边界篡改。
- 真正或签的通过/驳回并发测试断言事务回调同时活动数至少为 2、冲突和重试至少各 1 次，且最终恰好一项终态、一张投票、一条投票审计和一条结果通知。
