# ADR-0005：节点独立审核轮次与投票记录

## Status（状态）

已于 2026-08-11 接受，完整设计与书面版本均已由项目所有者确认。

2026-09-20 追加接受审核意见与多轮历史只读展示范围；不改变既有审批操作权限。

2026-09-23 追加接受处理页/审核页内的前序节点记录：共享折叠组件、实际路径顺序、默认最终结果、按需历史查询与独立草稿状态。

2026-09-23 追加接受局部交互优化：处理历史和审核历史独立加载/失败重试，每条保存及每轮审核默认折叠；视频固定弹层预览，返回当前表单只折叠与滚动，不刷新或改写草稿。当前节点内单条折叠复用已返回内容，不引入跨节点/账号私有数据缓存；整区收起、节点切换、页面隐藏、权限失效仍清空并在再次读取时重新授权。首次加载性能须以测量为依据，不削减后端权限/来源校验。

## Context（背景）

原流程允许节点处理人直接完成节点，再由下一节点负责人对上一节点发起驳回。真实验收表明该模型不符合业务责任边界：节点是否完成应由独立审核人确认，而不是由处理人自行决定。

每个节点还需要支持多名审核人的或签与会签、并发投票、审核时限、返工轮次、不可变历史和后续数据导出。把投票全部嵌入业务节点会扩大热点文档并增加并发覆盖风险；复用反馈或审计记录则会混淆处理事实、审核结论和安全审计三种不同职责。

## Decision（决策）

- 每个模板节点分别配置处理人和审核人，两组账号不得重叠。
- 处理人只能保存进度、标记受阻和提交审核，不能直接完成节点。
- 使用独立 `node_review_rounds` 集合保存每轮审核的快照、模式、时限和最终状态。
- 使用独立 `node_review_votes` 集合保存每位审核人的唯一不可变投票。
- 审核详情返回既有投票的 `comment`；节点记录页经独立受保护的 `listNodeReviewHistory` 按审核轮次倒序分页读取每轮的审批人显示名、决定、时间和意见。当前活动售后成员、负责人及既有超级管理员可只读查看，返工、多轮审核、完成或关闭后仍可追溯；不得因此放宽 `getReviewDetail` 或投票操作授权，不回写原票、不补造未保存的意见。缺失或空意见使用“未填写审核意见”，非字符串、超长、访问器或继承意见失败关闭。每页默认5轮、最多10轮，使用轮次游标而非固定历史总量窗口；每次响应前重新校验当前账号、售后关系和轮次版本。
- 投票编号由审核轮次和审核人账号编号确定性生成，相同请求幂等，不同内容冲突。服务入口继续接收 `approve/reject`，持久化投票、轮次结论和审计统一使用 `approved/rejected`；投票只保存事务内活动账号的受控显示名快照和内部账号编号，不信任客户端姓名。
- 或签任一通过即通过；会签必须全部通过；任一模式下任一驳回立即结束本轮并进入返工。
- 审核通过才完成节点并自动激活下一节点；末节点通过后完成业务线。
- 所有处理和审核写操作重新读取并校验当前账号、业务状态、节点关系、节点版本和审核轮次，不能依赖旧页面或微信身份回退授权。
- 提交审核的同请求重试也必须在服务端事务中先重新授权，再核对活动审核轮次、请求摘要、输入摘要和锁定版本；账号停用、处理角色移除或业务不再活动时不得借幂等结果继续访问。待审核节点会从锁定的最新反馈和分页凭证重新构建完整草稿，随后再次在事务内复核账号、业务、节点、活动轮次和最新反馈，并逐项比较草稿摘要、反馈修订、字段、凭证顺序和总字节数；不能信任审核轮次自身保存的摘要字段。
- 日历缺失时审核轮次同时保存处理时长待补算快照。`calendarSync` 在 `system_settings/calendar-review-processing-cursor` 保存只含文档游标和版本的安全扫描状态，每次最多扫描当前剩余额度且不超过 40 条；即使一页候选全部失效也推进游标，尾页后安全回绕，使第 41 条及后续有效候选可在有限调用内到达。逐条补算仍在固定文档事务中复核业务、节点、活动轮次、版本和待补算标记后同步更新节点与审核轮次；已经超过处理总时限的快照继续累计历史和本段逾期工作分钟。
- 终态投票以审核开始到决定时刻的工作分钟结算审核 SLA，保存已用、剩余、逾期分钟和日历版本。日历缺失不阻断通过或驳回，而是在不可变终态轮次保存独立审核时长补算边界；`calendarSync` 使用 `system_settings/calendar-review-timing-carryover-cursor` 公平扫描，允许旧轮次在返工、多轮审核、下游推进或整条业务完成后只修正时序元数据。一个终态轮次可同时含处理时长与审核时长两类补算，终态幂等版本链只接受零、一或两次已声明补算各自带来的精确版本提升。
- 新规则只作用于更新后的模板及其新建业务，旧业务不补造审核历史。
- 前序最终结果使用独立受保护只读接口 `getPreviousNodeResult`，校验目标确在当前查看节点之前且已完成，并复用最终字段来源证明；审核节点的字段、处理说明及全部凭证来自最终通过轮次，无审核节点来自最终完成反馈。读前及返回前复核当前字段权限、账号角色、售后/节点/来源状态，不扩展 `getReviewDetail` 或投票权限。历史无法证明最终来源时明确不可用，旧处理记录未留姓名快照时使用占位，不按当前账号姓名补造历史。组件单独管理展开、分页及附件预览，账号切换、页面隐藏或权限失效时清空；不能回填当前处理/审核草稿。

## Consequences（后果）

- 部署必须新增两个客户端不可直接读写的集合及相应唯一、列表和待办索引。
- 业务节点新增 `pending_review` 状态、处理/审核轮次和两类 SLA 运行字段。
- 小程序需要独立审核待办与审核页面，处理页面必须移除“直接完成”入口。
- 审核轮次只引用不可变反馈和已有凭证，避免重复上传云文件；原有 60 天凭证保留策略保持不变。
- 提醒工作器后续必须区分处理提醒和审核提醒，并按或签/会签的结束规则停止发送。
- 旧业务保留受控兼容边界；旧写入路由不得被用于绕过新审核规则。
- 真实 CloudBase 并发、索引、部署和微信开发者工具流程必须单独人工验收。
