# ADR-0009：业务发起人节点负责人及个人工时快照

## Status

状态：

已于 2026-08-18 接受并完成本地实现；模板策略、业务快照、处理轮归属、投票响应快照、日历补算、受保护运营明细接口与客户端明细展示均已实现，真实 CloudBase 部署尚未完成。

## Context

背景：

模板节点当前只能固化预选处理人，无法表达“谁发起业务，谁负责本节点”。运营看板已有节点累计 SLA 数据，但不能证明某一处理轮次由谁实际完成，也不能展示每位实际投票审核人的个人响应时间。查询时重新计算会受后来日历变化影响，也会把未参与者误当作零时长。

## Decision

决策：

- 每个新版审核模板节点使用 `processorAssignmentMode` 独立选择固定候选账号或实际业务发起人。
- 发起人模式在创建业务的事务中解析为唯一处理人；若发起人同时是该节点审核人，整笔创建失败关闭。
- 每个新审核轮次固化实际提交人的安全显示名称、负责人来源及本轮处理工作分钟；节点累计 SLA 字段继续保持原语义。
- 每条新审核投票固化从本轮审核开始到实际投票时刻的个人工作分钟；未投票人不产生记录。
- 日历缺失不阻断业务操作。新记录保存不可变边界并由有界 `calendarSync` 游标补算；历史记录缺少新字段时显示“历史数据未记录”，不推断或回填。
- 运营明细只投影安全显示名称和计时事实，不返回内部账号编号、OpenID 或请求摘要，也不生成绩效排名。

## Consequences

后果：

- 模板、业务快照、审核轮次、审核投票、日历补算和运营看板接口都需要同步扩展。
- 部署必须新增 `node_review_votes(reviewResponseTimingStatus ASC, _id ASC)` 与 `node_review_rounds(reviewStartedAt DESC, _id ASC)` 组合索引。
- 真实 CloudBase 的索引选择、事务竞争、多人会签和补算恢复需要单独验收。
- `workflowReminder` 与 `evidenceRetention` 的触发器策略保持不变。
