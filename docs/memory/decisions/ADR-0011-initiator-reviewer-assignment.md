# ADR-0011：业务发起人作为节点唯一审核人

## Status

已于 2026-08-24 接受。产品规则、角色冲突、快照、兼容、分享同步上线和验收设计均已由项目所有者确认。

## Context

现有模板节点只能配置固定审核账号。实际业务需要让某些节点（例如第二节点）由本次业务的发起人亲自审核，同时继续维持处理人与审核人的角色分离、不可变业务快照、提醒、双 SLA、个人响应时间和历史统计。

把“发起人”当作客户端传入账号会形成越权入口；在审核阶段重新回查业务创建人又会让模板修改和账号变化覆盖既有业务。系统还已经支持“业务发起人作为唯一处理人”，因此必须明确两个来源策略在同一节点冲突时的行为。

## Decision

- 每个新版审核模板节点增加 `reviewerAssignmentMode: fixed_accounts | business_creator`。
- 历史模板缺少该字段时按 `fixed_accounts` 兼容。
- `business_creator` 模式要求模板 `reviewerUserIds` 为空；业务创建事务内把当前活动发起人解析为唯一审核人并固化安全显示名称快照。
- 模板头保存绑定规范化节点定义的 SHA-256 `definitionDigest`；发起人审核模式不接受缺少摘要的模板。模板读取验证摘要，业务创建预约事务逐个固定读取当前源节点、重新计算摘要并与服务预读和模板头同时比较；预算同时计入源节点读取与业务节点写入且不得超过 100 次操作。
- 模板阶段禁止同一节点同时选择发起人处理和发起人审核；业务创建阶段再次禁止实际发起人与该节点解析后的处理人重叠。
- 冲突时整笔创建失败，系统不得自动删除处理人或允许同一人自审。
- 创建预约、最终发布及已发布幂等返回必须重新读取当前活动创建人，并严格校验业务的创建人、管理员和成员关系后再解释预约状态。
- 业务节点在创建时固化处理人和审核人显示名；新审核轮次与历史详情只复用该快照，不用参与人的当前账号姓名覆盖历史，旧业务缺失快照时显示固定安全占位。
- 下游审核、提醒、计时和运营统计继续使用统一的 `reviewerUserIds` 快照，不增加旁路授权或特殊统计口径。
- 旧业务不迁移，已创建业务不受模板后来修改影响。
- 现有七日公开节点固定快照与本功能共同进入小程序 `1.0.1`；其能力令牌、无需登录读取、七日有效期和凭证安全边界保持 ADR-0008 不变。

## Consequences

- 模板域、模板管理页面、业务创建快照、错误映射和相关测试需要同步扩展。
- 模板定义更新会改变 `definitionDigest`；直接绕过模板服务改写节点会使定义读取和新业务创建失败关闭。
- 不新增集合、组合索引或环境变量；现有下游主要通过解析后的审核人数组自然兼容。
- 必须回归审核待办、投票、提醒、个人响应时间、运营统计和公开分享，证明没有角色绕过或历史污染。
- 真实上线前需要上传新版 `businessApi` 和小程序 `1.0.1`，并在体验版完成发起人审核和微信好友/群公开分享验收。
