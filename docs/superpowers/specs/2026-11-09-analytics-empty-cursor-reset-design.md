# 运营统计空队列游标复位设计

## 目标与范围

减少运营统计队列耗尽后的重复空查询。仅修改 `cloudfunctions/operationsAnalytics/lib/cloud-analytics-repository.js` 中 node、decision、business、refresh 四类候选游标的领取路径。用户已确认本地实现和测试，暂不部署。

## 方案比较

采用复用现有游标的单次版本校验复位：尾页与首页均返回空后，将仍匹配所读版本和位置的游标写为 `cursorId: null`、`version + 1`。相比新增“已空”状态，保持现有数据结构且下轮仍直接发现新任务。跨调用缓存空结果或降低 Timer 频率会改变发现时效，不在本次范围。

## 行为约束

- 只有已存在的非空游标且两次查询均成功为空时，才尝试复位；缺失或已经为 null 的游标保持零写入。
- 事务内重新读取、校验游标 kind、位置和 version。已被其他工作器推进时不复位；不删除文档或覆盖新版本。
- 查询失败、损坏游标、版本溢出、写入或提交失败继续失败关闭；未知结果不拆单、不自动重放。
- 本轮返回空候选，下轮仍新鲜查询；空观察到复位之间新增的低 ID、高 ID 候选须能在后续调用发现。
- 非空领取、原筛选与排序、40 条批量、幂等统计发布、字段恢复独立游标、权限及 Timer 不变。原售后、站内提醒、企微及客户端均不修改。

## 成本与验收

四个旧游标同时耗尽时，完整 handler 的原空闲合成口径为每轮 5 次单读、9 次查询。拟改法首轮另外需要 4 次事务内游标读取、4 次游标写入和 4 笔事务；后续稳定空闲轮目标为原空游标口径的 5 次单读、5 次查询、0 写入。

对照须分别报告首轮、10 轮及 100 轮累计 SDK 读取、查询、写入、事务和返回字节。不能把少 4 次查询表述为整单降费比例；真实平台计费与线上游标分布需部署后另验。

测试覆盖四类游标、原本为空、正常回绕、新增低高 ID、并发领取和复位、事务重试、损坏及版本边界、读写和未知提交错误。所有合成业务、统计事实、通知及账号快照保持不变，只有自有统计游标允许变化。

## 实现补充

查询结果必须具有数组形状的 `data`，否则抛错，不把异常载荷当空队列并持久复位。仍复用原有领取事务，无新增字段或跨调用空结果缓存。本地新测试的原实现 RED 与候选 GREEN、完整统计/API/WXML 回归及首轮和 10/100 轮匹配计数见同名实施计划和忽略 Git 的 QA 回执；不据此宣称已上线或已取得现金降幅。
