# 业务发起人作为节点唯一审核人设计

日期：2026-08-24

状态：产品规则与完整设计已确认，允许直接生成实施计划并持续开发至功能落地。

## 1. 目标

每个新版审核模板节点可以独立选择审核人来源：

1. 固定审核账号；或
2. 实际业务发起人作为该节点唯一审核人。

选择业务发起人后，创建业务时必须在服务端事务内把当前活动发起人解析为不可变审核人快照。处理、审核、提醒、双 SLA、运营统计和历史读取继续消费统一的 `reviewerUserIds` 快照，不建立旁路授权。

本功能与已实现的七日公开节点固定快照共同进入小程序 `1.0.1`：已完成节点仍可由有权操作人生成固定快照并通过微信原生面板转发给好友或群。

## 2. 非目标

- 不修改已创建业务的审核人快照，也不迁移旧业务。
- 不改变或签、会签、驳回、返工、提醒、双 SLA 或个人响应时间口径。
- 不允许同一账号在同一节点同时处理和审核。
- 不把发起人在某节点的审核人身份传播到其他节点。
- 不允许客户端直接指定解析后的发起人审核账号。
- 不改变公开分享七日有效期、不增加永久公开地址，也不增加手动提前撤销。
- 不新增集合、组合索引或环境变量。

## 3. 模板审核人来源

### 3.1 数据契约

新版审核模板节点增加：

```js
reviewerAssignmentMode: 'fixed_accounts' | 'business_creator'
```

- 缺少该字段的历史模板节点按 `fixed_accounts` 兼容。
- `fixed_accounts` 要求 `reviewerUserIds` 为非空、严格、自有、无重复且符合账号索引预算的数组。
- `business_creator` 要求 `reviewerUserIds` 为空数组；未知值、访问器、继承值、稀疏数组、重复账号或模式与数组混用一律失败关闭。
- 字段进入模板节点规范化结果、持久化定义、可用模板投影和业务节点快照。
- 处理人来源 `processorAssignmentMode` 与审核人来源相互独立，每个节点分别保存，节点排序不得串改其他节点的来源。

### 3.2 管理端交互

节点编辑页在审核人区域提供两个互斥选项：

- 固定审核人；
- 业务发起人作为本节点唯一审核人。

选择业务发起人时：

- 清空并隐藏固定审核人选择器；
- 保存时只提交模式与空 `reviewerUserIds`；
- 只读模板页显示“业务发起人（唯一审核人）”。

切回固定审核人时必须重新选择至少一个活动审核账号，不能恢复已经清空的旧选择。

## 4. 双层角色冲突校验

模板保存和启用时，如果同一节点同时使用：

```text
processorAssignmentMode = business_creator
reviewerAssignmentMode = business_creator
```

立即以模板错误拒绝，不能保存或启用。

创建业务时，服务端在事务内读取当前活动发起人并解析全部参与账号。如果任一节点解析后的 `processorUserIds` 与 `reviewerUserIds` 有交集，整笔创建失败，稳定错误为：

```text
CREATOR_REVIEWER_CONFLICT
```

客户端统一显示：

```text
业务发起人不能同时担任同一节点的处理人和审核人，请调整模板或由其他账号发起
```

该校验覆盖两类冲突：

1. 同一节点的处理人与审核人都来自业务发起人；
2. 节点使用固定处理人，而实际发起人恰好位于固定处理人数组中。

系统不得自动删除处理人、静默改变模板或允许同一人自审。

## 5. 业务创建快照

业务创建服务在事务外只进行可失败的日历预计算，不信任客户端身份或模板缓存。最终创建事务必须重新读取并校验：

- 当前创建账号仍为活动账号；
- 模板仍处于启用状态且版本、节点数量和定义一致；
- 所有固定参与账号仍为活动账号；
- 解析后的处理人与审核人满足逐节点角色分离。

对于 `business_creator` 审核模式，业务节点写入：

```js
reviewerAssignmentMode: 'business_creator',
reviewerUserIds: [creator._id],
reviewerDisplayNames: [safeCreatorDisplayName]
```

对于固定模式，业务节点继续写入原固定审核账号及安全显示名称快照，并明确保存：

```js
reviewerAssignmentMode: 'fixed_accounts'
```

发起人跨节点、跨处理和审核角色参与时按内部账号编号去重读取；只有同一节点内的角色重叠被禁止。业务成员数组、索引字段字节预算和 CloudBase 100 次事务操作预算按解析后的实际账号计算。

同请求幂等重试先重新校验当前账号与业务关系，再返回已发布的原快照；模板后来修改不能改变已创建业务。

## 6. 审核、提醒与运营统计

业务创建已经把审核人来源解析成现有 `reviewerUserIds` 和显示名称快照，因此下游继续使用统一契约：

- 审核待办和审核详情只向当前活动且仍有权的快照审核人开放；
- 投票事务继续重读账号、业务、节点、审核轮次和确定性票据；
- 或签、会签、驳回和终态幂等语义不变；
- `workflowReminder` 继续只提醒尚未投票的实际快照审核人；
- 个人审核响应时间只记录实际投票人，未投票人不生成零时长；
- 运营统计把业务发起人作为普通实际审核人计入其投票事实，不创建特殊统计口径；
- 业务详情和历史投影可以显示审核人来源，但不得返回内部账号编号。

发起人账号若在创建后被停用，当前审核写入按既有规则失败关闭；历史业务和终态轮次仍由有权管理员按不可变显示名称快照读取，不回查当前姓名覆盖历史。

## 7. 公开只读分享同步上线

现有公开分享能力保持 ADR-0008 的安全边界，并纳入 `1.0.1` 验收：

- 只有审核通过且已完成的新版节点可生成快照；
- 只有活动业务成员中的业务管理员或该节点实际处理人可创建；
- 接收者持有不可预测能力令牌即可查看，无需登录或业务权限；
- 正文、结构化字段、处理说明和凭证清单在创建时固化；
- 图片、视频和 PDF 使用短期 HTTPS 地址，不公开永久 `fileId`；
- 分享最长有效七个二十四小时，到期后统一不可用；
- 原始凭证在分享有效期内增加保留锁，到期后恢复原保留规则；
- 发送者只能通过微信原生分享面板手动选择好友或微信群。

新审核人模式不修改既有分享头、分享块或令牌派生规则，也不改变已经创建的分享快照。

## 8. 安全与错误边界

- 模板关系字段必须是对象自身数据属性；访问器、继承值、稀疏数组和混合新旧结构失败关闭。
- 客户端不能提交 `createdByUserId`、解析后的审核人或显示名称；这些值只来自服务端当前事务。
- 账号、模板、节点版本或关系在计算窗口内变化时不写入旧快照。
- 所有错误只映射稳定中文，不返回内部账号、OpenID、请求摘要、集合名、索引或底层异常。
- 新模式不得降低现有处理人和审核人的每次写入重新授权要求。
- 不读取、不修改、不暂存或提交操作员自己的 `project.config.json` 修改。

## 9. 测试与验收

全部生产改动严格执行 RED → GREEN。自动化测试至少覆盖：

1. 历史模板缺字段默认固定审核人。
2. 两种审核人模式的严格规范化、持久化、只读显示和节点排序。
3. 业务发起人模式清空固定审核人，非法混用、访问器、继承值和稀疏数组失败关闭。
4. 模板阶段的双发起人角色冲突。
5. 创建时发起人唯一审核快照及安全显示名称。
6. 固定处理人包含实际发起人的创建冲突。
7. 同一账号在其他节点参与不受影响。
8. 创建账号停用、模板版本变化、幂等重试及 100 次事务预算。
9. 审核待办、投票、提醒、个人响应计时和运营统计回归。
10. 旧模板、旧业务和公开分享安全回归。
11. 完整 `businessApi`、`calendarSync`、`workflowReminder`、`evidenceRetention`、`operationsAnalytics`、小程序、WXML、语法、差异和项目记忆门禁。

体验版验收至少包括：

- 第二节点自动固化发起人为唯一审核人；
- 发起人获得待审核任务并成功投票；
- 同节点处理/审核冲突显示明确中文且不产生半成品；
- 已完成节点生成固定快照并通过微信转发给好友或群；
- 未登录接收者可以查看固化正文和图片、视频、PDF；
- 公开页不显示永久文件编号、账号标识或内部预约数据。

真实 CloudBase 部署只需更新 `businessApi` 和小程序版本；公开分享的两个集合、索引和密钥保持现状。定时函数的正式触发器配置不因本设计自动改变。
