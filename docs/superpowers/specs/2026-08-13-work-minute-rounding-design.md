# 工作时长完整分钟折算修复设计

## 1. 背景与根因

真实 CloudBase 隔离验收中，处理人已成功保存处理进度，节点、反馈和凭证关联均完整，但后续“提交审核”稳定返回 `VERSION_CONFLICT`，且没有创建任何审核轮次。

根因位于工作时长的数据边界：节点开始时间和提交时间都保留秒与毫秒，`workingMinutesBetween` 因而可能返回非整数分钟，例如 12.35 分钟。审核服务和审核仓储要求持久化的已用、剩余与逾期工作分钟都是安全整数，因此把合法的秒级时长误判为版本或快照冲突。

这不是真实并发修改，也不是节点、反馈、凭证或审核人数据损坏。

## 2. 已批准规则

`businessApi` 中凡是要写入业务节点、审核轮次或补算快照的工作时长，统一采用“已经完整经过的工作分钟”：

- 非负秒级结果按分钟向下取整。
- 59 分 59.999 秒记为 59 分钟。
- 60 分 00 秒记为 60 分钟。
- 不允许通过四舍五入提前累计工作分钟或提前判定逾期。
- 精确的开始、结束和决定时间戳继续原样保存，只有累计工作分钟使用整数。

提醒工作器继续使用现有的精确秒级阈值判断，本修复不改变整小时提醒语义。

## 3. 实现边界

修复应放在 `businessApi` 的权威工作时间服务输出边界，使提交审核、审核投票结算和后续调用者得到同一种整数分钟语义，避免只在某一个入口临时修补。

本次不做以下变更：

- 不修改客户端请求结构或两步提交幂等键。
- 不修改 `business_nodes`、`node_feedback`、`node_review_rounds` 或凭证的数据结构。
- 不修改日历工作日、09:00—20:00 工作时段或 SLA 小时配置。
- 不修改 `workflowReminder` 的秒级提醒判断。
- 不手工修改或迁移已经保存的节点、反馈和凭证。

## 4. 数据流与恢复行为

处理人再次点击“提交审核”时：

1. 服务端重新读取活动账号、业务、当前节点和最新已发布反馈。
2. 工作时间服务按权威日历计算秒级覆盖区间，并返回向下取整后的完整工作分钟。
3. 审核服务据此生成整数的已用、剩余和逾期分钟快照。
4. 审核事务继续执行既有版本、参与账号、草稿摘要和凭证关联校验。
5. 校验通过后创建审核轮次，并把节点切换为 `pending_review`。

已有的处理进度和凭证不需要重新上传；修复部署后可直接重试“提交审核”。

## 5. 错误与安全边界

- 日历缺失仍返回既有 `pending_calendar` 结果，不伪造分钟。
- 负时间、无效日期、非有限数或超出安全整数范围仍失败关闭。
- 真正的节点版本、轮次、反馈摘要或授权冲突仍返回原有安全错误，不因取整而被放宽。
- 不增加包含业务正文、账号身份或凭证路径的日志。

## 6. 测试与验收

实施必须先增加失败测试，再修改生产代码：

1. 工作时间服务覆盖 59 分 59.999 秒、60 分 00 秒和带小数的跨工作时段结果。
2. 提交审核覆盖非整分钟处理时长，并成功创建整数时限快照。
3. 审核投票结束覆盖非整分钟审核时长，确保已用、剩余和逾期分钟均为整数。
4. 日历缺失、整分钟、跨非工作日及既有提醒边界保持回归通过。
5. 运行完整 `businessApi`、`calendarSync`、`workflowReminder`、`evidenceRetention`、小程序和 WXML 门禁。

真实验收在修复版 `businessApi` 部署后进行：复用当前已保存草稿直接提交审核，确认创建一条审核轮次、节点进入待审核状态、审核截止时间出现，且原反馈和凭证引用保持不变。
