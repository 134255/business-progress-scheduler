# 项目长期记忆系统设计

## 目标

为 Codex 建立可跨任务恢复的项目记忆，降低开发后期因上下文丢失、状态误判和技术决策遗忘造成的返工。采用“全局通用 Skill + 每个 Git 仓库独立记忆文件”的方式，确保不同项目互不污染，并让记忆与代码版本保持一致。

## 方案选择

采用方案 2：全局安装 `maintaining-project-memory` Skill，在每个项目仓库中分别维护权威记忆文件，并与对应功能代码放在同一个 Git 提交中。

不采用以下方案：

- 仅依赖 Markdown：结构简单，但无法稳定约束任务开始和结束时的读写行为。
- 仅依赖 Claude-mem 或其他自动会话存储：自动化程度高，但可能记录噪声、产生额外运行开销，并存在敏感信息和摘要失真的风险。

## 架构

### 全局 Skill

在 Codex 的个人 Skills 目录创建 `maintaining-project-memory`。该 Skill 只保存通用流程，不保存任何具体项目内容。

触发场景包括：

- 开始、继续或恢复一个项目开发任务；
- 用户询问项目进度、历史决策、阻塞项或下一步；
- 完成功能、修复、重构、验证、交接或准备 Git 提交；
- 发现当前代码与既有项目记忆可能不一致。

### 仓库记忆文件

当前项目新增以下结构：

```text
AGENTS.md
docs/memory/
├── PROJECT.md
├── STATUS.md
└── decisions/
    └── ADR-0001-*.md
```

- `AGENTS.md`：项目级入口规则，要求开始任务时读取记忆，完成任务时同步更新；声明事实优先级和安全边界。
- `PROJECT.md`：稳定事实，包括产品目标、范围、架构、数据模型、权限规则、运行环境和长期约束。
- `STATUS.md`：易变事实，包括当前阶段、已完成、进行中、阻塞项、验证证据和下一步。
- `decisions/`：每个重大、长期有效的技术决策单独建立 ADR，记录背景、决定、备选方案、原因和影响。

Git 历史承担时间线和变更追踪职责，因此不额外维护重复的手工变更日志。

## 事实优先级

当信息冲突时按以下顺序处理：

1. 可复现的测试、构建和运行结果；
2. 当前代码与配置；
3. Git 提交历史和差异；
4. 项目记忆文件；
5. 会话摘要或模型推断。

不得使用旧记忆覆盖当前事实。发现冲突时，应先核实再更新记忆，并明确记录尚未确认的事项。

## 数据流

### 任务开始

1. 定位 Git 仓库根目录。
2. 读取适用范围内的 `AGENTS.md`。
3. 读取 `PROJECT.md` 和 `STATUS.md`。
4. 仅在任务相关时读取对应 ADR，避免无关上下文膨胀。
5. 对照工作区状态、近期提交、代码和测试，识别过期记忆。
6. 基于已验证事实继续任务，不把推测当成现状。

### 任务进行中

仅记录具有长期价值的变化：

- 已实现能力和真实完成状态；
- 架构、接口、数据结构与权限约束；
- 重要决策、被否决方案及原因；
- 已知问题、外部依赖和阻塞项；
- 验证命令、结果与尚未覆盖的风险；
- 下一次可直接执行的具体步骤。

### 任务结束

1. 执行与风险相称的测试和差异检查。
2. 根据证据更新 `STATUS.md`。
3. 稳定事实变化时更新 `PROJECT.md`。
4. 产生重大且长期有效的决策时新增 ADR。
5. 检查记忆中是否存在占位符、矛盾、未经验证的完成声明或疑似敏感信息。
6. 将记忆文件与对应功能代码放入同一个 Git 提交。

纯解释、只读检查或没有改变项目事实的任务不更新记忆，避免无意义提交。

## 安全与隐私

禁止写入：

- AppSecret、访问令牌、密码、Cookie、私钥和验证码；
- 用户隐私、个人身份数据和未脱敏的业务数据；
- 临时凭证、完整环境变量值和本地认证信息；
- 大段聊天记录、终端日志或可从代码直接读取的琐碎内容。

允许记录凭证的变量名、配置位置和获取流程，但不得记录真实值。遇到疑似敏感内容时应省略具体值，并提示用户采取轮换或清理措施。

## 错误处理

- 记忆文件缺失：对当前明确授权的项目执行初始化；对其他项目先说明并取得写入授权。
- 工作区存在用户改动：保留并隔离处理，不覆盖、不重置、不把无关改动混入提交。
- 验证失败：在 `STATUS.md` 中记录为失败、阻塞或未验证，不得标记完成。
- 信息不确定：标记为“待确认”，并记录获得证据所需的下一步。
- 记忆过长：将稳定信息保留在 `PROJECT.md`，当前状态保留在 `STATUS.md`，历史原因下沉到 ADR；删除已失效且可由 Git 恢复的重复内容。
- Skill 不可用：项目文件仍可作为降级记忆，按 `AGENTS.md` 中的流程人工读写。

## Skill 验证设计

遵循 `skill-creator` 与 `superpowers:writing-skills` 的 RED-GREEN-REFACTOR 流程。

### RED：无 Skill 基线

使用不接触正式项目内容的隔离测试代理执行压力场景，观察并记录其是否：

- 跳过既有记忆直接开始工作；
- 把未经验证的功能写成已完成；
- 将敏感值或大段日志写入长期记忆；
- 在脏工作区中覆盖或混入无关改动；
- 完成功能后忘记同步状态。

至少覆盖时间压力、用户要求快速完成、已有未提交改动三种组合压力。

### GREEN：加载 Skill

对相同场景加载 `maintaining-project-memory`，确认代理能够：

- 先读取项目入口和记忆文件；
- 使用代码、测试和 Git 证据校验状态；
- 仅写入长期有效的信息；
- 排除敏感值与无关日志；
- 把记忆更新与对应功能改动同步管理。

### REFACTOR：关闭漏洞

根据 GREEN 阶段出现的新遗漏，补充明确规则和常见错误，再重复场景，直到结果稳定。

### 结构化检查

- 使用 `skill-creator` 的 `quick_validate.py` 检查 Skill 名称、YAML 和目录结构。
- 运行本地校验脚本检查必需文件和章节、占位符以及疑似密钥模式。
- 检查 `git diff --check` 和目标提交范围。

隔离测试代理不得修改正式项目目录；测试产物使用临时目录，验证完成后不纳入项目提交。

## 成功标准

- 新任务能够仅依靠仓库文件恢复产品目标、架构、当前进度、阻塞项和下一步。
- 不同项目的具体记忆不会互相读取或写入。
- 功能提交包含与其相关的状态或决策更新；无事实变化时不制造记忆提交。
- 任何“已完成”声明都有代码、测试、构建或人工验收证据。
- 记忆文件不含真实密钥、令牌、密码或个人隐私数据。
- Skill 通过结构校验、基线对照场景和加载后行为验证。

## 当前项目初始化内容

首次初始化将以现有代码、技术规划、数据模型、开发排期、Git 历史和本地测试结果为证据，建立：

- 小程序的目标、技术栈、业务线与节点权限模型；
- 当前已实现功能和未完成的云开发联调事项；
- 真实 AppID、云环境和部署状态等阻塞项；
- 下一阶段可以按顺序执行的配置、部署和验收工作。

初始化不会把当前工作区中用户尚未提交的业务改动重写或清除。
