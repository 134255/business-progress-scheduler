# 节点处理保存后加载态释放设计

## 背景与根因

节点处理页执行“保存处理进度”时，会以操作开始时的节点版本创建不可变操作上下文，并设置 `submitting: true`。服务端保存成功后节点版本递增，页面随即调用 `loadData()` 刷新到新版本。现有 `finally` 复用严格的 `writeStillCurrent()`：该函数要求页面当前节点版本仍等于操作开始时的旧版本，因此合法刷新后返回 `false`，`submitting` 无法恢复为 `false`。三个操作按钮都绑定同一个 `loading` 状态，于是持续转圈，直到退出并重新进入页面。

## 目标

- 保存成功并刷新到新节点版本后，当前操作必须解除 `submitting`，三个按钮恢复正常状态。
- 保留现有严格异步写回保护：旧账号、旧页面、旧节点、旧操作序号或旧节点版本的结果不得继续修改业务数据或显示成功结果。
- 账号切换、页面卸载、导航到其他业务/节点或后续操作已开始时，旧操作的 `finally` 不得清除新页面或新操作的加载态。
- 不修改服务端接口、节点版本规则、幂等请求键或数据库结构。

## 设计

在 `miniprogram/pages/node-feedback/index.js` 中把两种职责拆开：

1. `writeStillCurrent(operation)` 保持现有严格语义，继续校验账号、页面存活、业务编号、节点编号、操作序号和操作开始时的节点版本。它用于上传、登记、保存结果、成功提示等业务写回边界。
2. 新增一个仅用于释放当前操作 UI 状态的判断，例如 `operationStillOwnsPage(operation)`。它校验：
   - 操作对象存在；
   - 页面仍存活；
   - 当前账号仍是操作账号；
   - 当前业务和节点仍与操作一致；
   - `writeSequence` 仍等于该操作序号。

该 UI 判断故意不比较节点版本，因为成功后的权威刷新必然可以合法提升节点版本。`performProgressAction()` 的 `finally` 仅在该操作仍拥有当前页面加载态时执行 `setData({ submitting: false })`。其他处理结果和异常路径继续使用严格的 `writeStillCurrent()`，不放宽安全边界。

## 测试

先在 `miniprogram/test/review-flow.test.js` 增加失败回归：

- 保存处理进度返回新节点版本；
- 随后的 `loadData()` 读取新节点版本和最新反馈；
- 操作完成后断言 `submitting === false`；
- 断言三个按钮仍使用同一 `submitting` 状态，避免只修一个按钮。

同时保留并复跑现有账号切换、页面卸载、节点切换、等待期输入冻结、两步幂等提交和上传异常测试，证明新判断只释放本次 UI 状态，不允许旧业务结果写回。

## 验收

修复部署并重新编译后，在隔离业务的活动处理节点保存一次无敏感处理说明：页面显示保存成功和新反馈历史，短暂加载结束后，保存处理进度、标记受阻、提交审核三个按钮都恢复为可操作状态，无需退出页面重进。
