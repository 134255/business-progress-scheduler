# 停用参与人历史业务详情读取修复设计

日期：2026-08-14（Asia/Shanghai）

## 背景

真实 CloudBase 提醒停止条件验收中，操作员停用一名普通处理人后，活动超级管理员打开一条包含该参与人的已完成业务时收到 `FORBIDDEN`；重新启用该普通账号后，同一超级管理员立即恢复读取。

生产代码中的业务详情投影会为所有节点处理人、审核人或旧负责人实时读取账号名称。当前实现把“参与账号必须为 `active`”作为生成显示名称的前置条件，因此任一历史参与人被停用都会阻断整条业务详情。该条件混淆了两类职责：当前访问者授权与历史参与人显示。

## 目标

- 活动且原本有权的访问者可以继续查看包含停用参与人的业务详情，包括已完成、已取消和已关闭业务。
- 停用参与人的名称显示为“安全名称（已停用）”。
- 当前访问者授权、业务成员边界、写入权限、审核权限和提醒停止规则保持不变。
- 不迁移或改写既有业务、节点、审核轮次、凭证、通知和审计记录。

## 非目标

- 不让超级管理员自动越过业务成员关系查看任意业务。
- 不允许停用账号登录、处理、审核、修改业务或接收提醒。
- 不在本次新增业务节点姓名快照字段，也不从审核轮次反推节点参与人。
- 不改变账号停用、重新启用和模板负责人校验流程。

## 方案

业务详情继续先重新读取并验证当前访问者。当前访问者必须存在、状态为 `active`，并满足原有业务成员或旧版 OpenID 兼容关系；这些检查不变。

节点参与人名称解析调整为只读显示规则：

1. 参与账号文档必须存在，且文档编号与节点关系中的内部账号编号严格一致。
2. 账号状态严格为 `active` 时，返回现有安全名称。
3. 账号状态严格为 `disabled` 时，返回“现有安全名称（已停用）”。
4. 账号状态缺失、类型错误或为其他未知值时失败关闭。
5. 显示名称仍只接受账号自身的数据属性 `displayName` 或 `username`；空值、超长值、控制字符、访问器和继承值仍失败关闭。
6. 账号文档缺失时仍失败关闭，不伪造姓名或责任关系。

该规则只影响 `getBusinessLine` 返回的处理人、审核人和新版旧负责人显示文本。服务端保存、提交审核、投票、模板启用和提醒工作器继续各自重新读取账号状态并要求参与账号活动，不复用显示层判断。

## 数据流与安全边界

1. 受保护路由解析当前会话账号。
2. 业务仓储重新读取当前账号和业务关系，完成原有访问授权。
3. 仓储读取业务节点并汇总需要显示的内部参与账号编号。
4. 显示名称缓存逐账号读取文档，严格校验编号、状态和安全名称。
5. 活动名称原样进入安全投影；停用名称追加固定中文状态后缀。
6. 返回前事务继续重新验证当前访问者、业务状态与节点版本，防止查询期间撤权或状态变化。

客户端只接收显示字符串，不接收参与账号编号、OpenID、账号状态原值或其他账号字段。

## 错误处理

- 当前访问者停用或失去业务关系：继续返回 `FORBIDDEN`。
- 历史参与账号为 `disabled`：允许读取并追加“（已停用）”。
- 历史参与账号缺失、状态损坏或名称损坏：继续返回 `FORBIDDEN`。
- 查询期间当前访问者、业务或节点发生变化：沿用现有 `FORBIDDEN`、`NOT_FOUND` 或 `VERSION_CONFLICT` 边界。
- 不把数据库错误、账号编号或底层详情投影给客户端。

## 测试与验收

按 TDD 执行：

1. 新增仓储失败测试，构造活动业务成员读取包含停用处理人的已完成业务；当前实现必须以 `FORBIDDEN` 失败。
2. 修复后断言详情成功，停用处理人显示“安全名称（已停用）”，活动审核人名称保持不变。
3. 保留并补强当前访问者停用、参与账号缺失、未知状态及非法名称失败关闭测试。
4. 复跑业务仓储聚焦测试与 `businessApi` 全量测试。
5. 运行 JavaScript 语法检查、`git diff --check` 和项目记忆校验。
6. 重新部署 `businessApi` 后，在目标环境停用专用普通账号，确认活动超级管理员仍能查看包含该账号的已完成业务且显示停用标记；再确认停用账号自身无法登录或写入、提醒工作器仍不为其创建提醒。

真实 CloudBase 部署和多账号复验在执行前均保持 `unverified`。
