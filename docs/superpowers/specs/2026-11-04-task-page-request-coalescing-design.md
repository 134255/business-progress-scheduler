# 详情及待办页在途读取合并：短设计

日期：2026-11-04（Asia/Shanghai）。状态：用户已确认按此设计在当前工作区本地实现，并允许保留、提交和部署；实施及发布证据另行记录，不以授权代替完成。

## 目标与范围

在不改变页面数据、权限、分页及错误语义的前提下，减少同一页面中重叠的相同读取。仅涉及：

- `miniprogram/pages/business-detail/index.js` 的详情加载。
- `miniprogram/pages/pending-processing/index.js` 的第一页刷新。
- `miniprogram/pages/review-list/index.js` 的第一页刷新。

不包含售后列表、已优化的首页、节点工作区重构、商品联动、附件预览或上传进度优化。不改云函数、服务接口、数据库、索引、依赖、权限、提醒、业务写入或站内通知。

## 方案比较

- **页面私有的在途读取合并（用户已选择的方向）**：同一页面、同一会话与请求代际内等待同一笔未结束的读取，不保留已完成响应。沿用首页已验证的边界，不引入全局缓存。
- 全局跨页面合并：更容易把不同页面生命周期及刷新边界混在一起，本次不采用。
- 已完成结果缓存或减少重新进入时的刷新：可能显示旧权限或旧任务，违背保留原刷新语义的要求，不采用。

## 必须保留的刷新边界

1. 合并键包括页面实例、当前账号对象及账号编号/角色、目标售后或固定第一页查询参数、页面请求代际。不同账号、角色、会话对象、目标或代际绝不合并，不缓存授权结论。
2. **每次 `onShow` 都开始新一代读取**，即使没有先收到 `onHide`，也不加入旧请求。离开、卸载、清空私有状态或发现账号失效，使原在途记录及迟到结果失效；不能主动取消已经发生的云端计费。
3. 详情页保存、关闭、驳回、人工路线决定等业务操作后的刷新，以及版本冲突后的刷新，必须另起请求，不能加入操作前的读取。所有业务操作及幂等键保持原样。
4. 待处理及待审核的加载更多沿用原分页与去重逻辑，不与第一页刷新合并。第一页刷新覆盖旧分页请求时，仍保持既有新请求优先规则。
5. 同一代的重复普通加载或重试等待同一笔请求。成功或失败结束后立即释放记录；之后主动刷新必须重新读取，不新增TTL、持久缓存或自动重试。
6. 旧请求完成或失败时，只能清理自己的记录，不能清空新请求的加载状态、页面数据或错误。同步抛错也不能留下无法释放的在途记录。
7. 保留原页面展示和错误分类；已有详情继续后台刷新，不清空已渲染内容。账号失效仍清除其私有投影，不因复用请求延迟失效处理。
