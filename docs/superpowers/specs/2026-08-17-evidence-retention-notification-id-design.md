# 凭证保留提醒通知编号兼容设计

## 背景与根因

`evidenceRetention` 已在真实 Timer 验收中成功创建提前 15 天提醒，数据库记录、收件人和通知类型均正确，但目标账号的小程序通知中心不可见。

根因是两个云函数之间的编号契约不一致：

- `evidenceRetention` 使用 `evidence-retention:<businessLineId>:<days>` 作为确定性通知编号；
- `businessApi` 的通知读取与标记已读边界复用了普通文档编号规则，只允许字母、数字、下划线和连字符；
- 编号中的冒号因此被错误拒绝，合法提醒在二次授权投影阶段被过滤。

## 方案比较

### 方案 A：通知专用严格兼容（采用）

保留现有确定性编号，同时让通知边界接受两类编号：

1. 现有普通通知编号；
2. 严格匹配 `evidence-retention:<合法业务编号>:1|7|15` 的保留提醒编号。

优点是现有提醒立即恢复可见，不迁移数据、不产生重复提醒，并且冒号只对一个固定前缀和三个合法天数开放。

### 方案 B：更换为哈希编号

让后续保留提醒改用不含冒号的哈希编号。新记录可见，但现有提醒仍不可见；若不增加迁移或双读逻辑，还会产生重复提醒，因此不采用。

### 方案 C：全面放宽普通文档编号规则

允许所有业务文档编号包含冒号。改动面过大，会影响账号、业务、节点、轮次、凭证等无关边界，因此不采用。

## 详细设计

### 编号校验

在审核与通知服务中新增通知专用编号校验，不改变通用 `DOCUMENT_ID`：

- 普通通知继续使用现有 `DOCUMENT_ID`；
- 保留提醒仅接受固定前缀 `evidence-retention:`；
- 中间业务编号必须满足现有业务文档编号字符和长度规则；
- 末段只允许 `1`、`7` 或 `15`；
- 空值、额外分段、路径字符、其他天数、超长业务编号和其他任意冒号编号均拒绝。

### 数据流

1. `listMyNotifications` 仍按当前活动账号查询定向通知或超级管理员角色通知。
2. 二次事务授权读取通知时使用通知专用编号校验。
3. 返回结果继续只投影安全字段，不增加凭证内容、文件路径或账号编号。
4. `markNotificationRead` 在服务入口使用同一个通知专用编号规范化函数，再由仓储重新校验当前账号和收件关系。
5. 已读标记仍使用通知编号和账号编号的哈希，不改变现有记录结构。

### 兼容与安全

- 不修改现有 `notifications` 记录，也不重新运行 `evidenceRetention`。
- 已产生的 15 天提醒在重新部署 `businessApi` 后应直接可见并可标记已读。
- 处理提醒、审核提醒和其他普通通知行为保持不变。
- 非收件人、停用账号、损坏收件人数组、未知通知类型和非法冒号编号继续失败关闭。

## 测试设计

测试必须先失败再实现：

1. 仓储列表能够返回合法的 1、7、15 天保留提醒。
2. 合法保留提醒可创建当前账号独立的已读标记。
3. 服务层 `markNotificationRead` 接受合法保留提醒编号。
4. 错误前缀、非法天数、路径字符、额外冒号、空或超长业务编号均被拒绝。
5. 原有普通通知、收件人隔离、角色通知、账号停用和标记碰撞测试保持通过。

完成聚焦测试后运行 `businessApi` 全量、WXML 结构、语法、差异和项目记忆校验。

## 部署与验收

只需要重新部署 `businessApi`；`evidenceRetention`、数据库记录和触发器配置均不变，三个定时云函数继续保持空触发器。部署后使用原收件账号重新进入通知中心，确认现有 15 天提醒可见、跳转安全并可标记已读，再继续第二次幂等 Timer 验收。
