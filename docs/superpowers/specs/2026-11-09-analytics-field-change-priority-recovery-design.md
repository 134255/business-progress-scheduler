# 字段统计降本：变更优先与有界完整修复

## 状态与范围

2026-11-09：用户确认本设计和实施计划，选择原生执行。已完成本地实现、30组合成净操作测试及独立整体复核所提问题的TDD修正，全量回归通过；精确证据见STATUS及本计划ledger。默认仍旧模式，未进行云部署。验收证据见 `docs/deployment/analytics-field-change-priority-recovery-acceptance.md`，本文件不是云部署授权或现金降幅承诺。

本轮只推进降本清单的第一项——运营字段统计恢复。企微非工作时间进度写入、原站内提醒候选过滤是后续独立事项，不混入本次运行改动。沿用当前 CloudBase/Node.js 项目，不迁移数据库，不购买产品，不引入付费消息队列。

## 意图和依据

已完成但内容未变的节点，目前仍在每次字段恢复调用中重新加载来源、复核投票和写扫描游标。相同快照不重复写已经实现，四候选来源预读、连续排除节点检查点合批和四类空候选游标复位也已实现，不能重复计算其收益。

本地真实 handler＋合成数据库基线：30 个未变化的完成节点，每轮 get/query/set/transaction 为 185/21/30/60；30 个审核完成节点为 275/51/30/60，连续三轮均生成 0。相关来源恢复测试 64/64 通过。这些是 SDK 边界尝试计数，不是现金计量或单函数线上成本归因。

当前 `businessApi/index.js` 在业务成功后调用内部 `operationsFieldService.refreshAfterMutation`；仓储覆盖提交反馈、保存并提交审核、提交审核、投票及人工路线决定五类即时刷新。其失败不会逆转业务成功。该通路可保留，新增队列承担确定的变更发现与失败恢复，完整巡检捕捉漏标记、历史和旁路写入。

## 目标、非目标及不可接受结果

目标：

- 不变历史不再每次定时调用都进行完整来源恢复；有变更先处理；漏标记仍能恢复。
- 把登记队列、分页、确认、巡检调度、冲突、读写字节及事务成本全部纳入新旧对照。
- 保留原即时刷新和看板/导出的请求驱动回源、首末权限检查、来源完整性与不完整结果语义。
- 整体实测有净收益才建议发布；不把 SDK 请求减少冒称账单现金按比例下降。

非目标：改原工时事实阶段、原售后内容/进度/版本/更新时间、站内通知/计数、企微规则/名单/三小时计时、客户端接口或交互、日历、文件保留、搜索、Timer、IAM、依赖或规格。

不可接受：为省钱跳过权限/来源/投票复核；让统计失败导致业务失败；因旧队列完成通知吞掉新变更；因繁忙队列停掉完整修复；把等待巡检说成已恢复；以空队列证明历史完整。

## Approaches：选择和取舍

1. **仅合并成熟节点游标写入**：不改变来源发现，范围较小，但主要节省检查点写入/事务，保留大多数历史读取。本次未选择。
2. **变更优先＋有界完整修复**：私有队列合并真实变更，保留即时刷新；低频启动完整巡检、积压时连续续跑。减少正常历史扫描，增加每次业务变更的少量队列读写与调度状态。用户已确认本方向及本文件参数/契约。

不采用只比 sourceHeader/旧快照就免检，也不关闭完整修复；sourceHeader 不是权威内容签名或权限能力。

## 已确认参数（2026-11-09）

- 保留现有平台 Timer，不新增或降频 Timer；真实线上触发间隔部署前另行只读核验。
- 完整巡检完成后，等待 60 分钟再启动下一轮；首次进入新模式立即开始兼容巡检。
- 巡检一旦启动，每次后续受信 Timer 都继续，直到真正遍历到尾部，不在页与页之间再等待一小时。
- 字段阶段仍在原工时阶段之后，总计最多 40 个原始节点候选、5 秒协作预算；原最多 50 张审核票和每事务最多 100 次操作不扩大。
- 巡检应运行时，先给巡检最多 8 个原始候选的配额，再给优先队列剩余配额；队列严格为空时，可把未用配额返给同轮巡检，总计仍不超过 40。不在繁忙队列之后才尝试巡检。
- 每次最多访问 8 个队列工作项，每个售后工作项单次最多预备 8 个节点；所有返回的节点页、待确认节点重访均计入共同候选预算，不靠重分配制造额外扫描。

60 分钟是两次完整巡检之间的等待时间，**不是修复完成 SLA**。失去变更标记的数据可能等待下一轮启动，再加实际触发间隔、分页次数、已有积压和真实 SDK 耗时；源码错误、永久超时或持续来源损坏没有有限完成保证。测试报告必须列出实际虚拟时钟延迟及健康前提，不能只列批量上限公式。若这一恢复时效不被接受，应在确认设计前调整参数。

## 组件和数据

### 1. 私有变更队列

新增 `operations_field_refresh_queue`，只允许云函数/服务端读写；客户端不得直接访问，不新增公开 HTTP 或客户端 action。

一个售后最多保留一条待处理工作项。确定性 `_id` 由用途前缀和售后内部编号的 SHA-256 生成；文档只保存 schemaVersion、businessLineId、enqueueToken、revision、扫描 afterNodeId、待确认节点编号清单及其必要状态、更新时间。不得复制账号资料、字段值、反馈、票意见、客户信息、文件地址、权限快照或密钥。

- `enqueueToken` 是服务端每次逻辑登记生成的随机非授权代际标记，不是密码/访问令牌。即使旧文档已经删除、新文档 revision 从头开始，旧完成请求也不能匹配它，避免删除重建的 ABA 问题。
- 同售后再次登记生成新 token，重置其节点扫描到起点，并递增合法 revision；并发事务重试必须重新读取当前队列状态。溢出、坏字段/原型/访问器拒绝，不能悄悄覆盖损坏记录。
- 不按人数或姓名建立队列，也不把队列内容用作业务归属或权限凭证。
- 队列本身仅使用 `_id` 排序/续页，正常完成时按代际条件删除；不增加 pending 状态组合索引。售后内节点发现复用已有 `businessLineId,_id` 索引；上线前须核对真实计划，不假定文档中列出的索引已经存在。

### 2. 控制状态

新增私有 `system_settings/operations-field-recovery-state-v1`，保存严格 schema、revision、队列轮转位置、巡检代际、active/nextRepairAt 和必要更新时间；不含业务正文或账号身份。

保留原 `system_settings/operations-field-snapshot-cursor` 的严格 schema 和内容，不向它添加新字段。完整巡检继续用原 keyset、CAS、单条锚点及连续排除后缀逻辑；新的控制状态只决定何时启动/续跑、何时确认完成。

未到巡检时间且队列严格为空时，只进行必要状态/队列发现，不读旧节点来源、不更新“最后检查时间”制造空转写入，也不持久缓存“已空”。每次受信调用仍新鲜检查。

## 业务变更接入

在现有 API 已确认业务成功之后、原字段即时刷新之前，调用服务端私有 enqueue 方法；登记和即时刷新分别捕获失败，任一失败均不抹掉另一条恢复机会，不改变原业务返回值/错误、幂等结果或搜索/卡片收尾。

候选覆盖表（逐项使用当前源代码和测试确认，不扩展业务动作本身）：

| 已有动作 | 登记范围与原因 |
| --- | --- |
| submitFeedback、saveAndSubmitNodeForReview、submitNodeForReview | 当前已发布来源/完成、审核状态变化；登记所属售后 |
| submitReviewVote | 从当前受保护审核轮次定位售后；票决/终态可能影响节点和售后头 |
| decideNodeRoute、decideOptionalTailNode | 实际路线和完成状态影响此前及当前样本 |
| rejectPreviousNode | 当前/上游节点状态与已发布来源可能失效；按售后覆盖 |
| updateBusinessMetadata | 快照中的业务显示信息变化，不能只处理当前节点 |
| closeBusinessLine、amendFrozenBusiness | 售后资格、冻结/审计修订及头信息变化；按售后覆盖 |

`createBusinessFromTemplate` 不产生最终完成字段样本，第一版不为纯创建登记；后续完成动作已覆盖，完整巡检仍覆盖历史。正式默认 legacyRoutes 当前仅 profile/dashboard，文件中未注册的旧 update/delete/feedback 函数不当作现网入口。测试必须对以上真实可达动作及失败/幂等返回做接入覆盖，不能靠函数名猜测。

业务编号来自当前受保护结果，必要时从当前节点/审核轮次解析并校验归属；不能把一个未被业务操作采用的客户端字段当作可信目标。新方法保持内部注入契约，不放开任意客户端入队能力，不修改原业务事务或消耗其 100 操作预算。

登记采用独立、有限的服务端事务，只有 SDK 原有冲突语义可重试；未知传输/提交结果不在同一请求拆单重放。进程在业务提交后、登记前退出，或登记明确失败，属于完整巡检负责的已知窗口。原五类同步字段刷新照常执行；其他头/路线变更由优先队列加快恢复。不会承诺恰好一次执行或零额外延迟。

## 队列处理、并发与公平性

1. 只在原受信 Timer 字段阶段内部执行，不接受事件载荷指定队列、时间、跳验或强制完成。
2. 队列 `_id` keyset 使用独立持久轮转位置；尾部回绕。不固定每次从最小编号开始；坏项、热点售后、失效项不能永久阻挡其他工作项。
3. 每条售后工作项按当前 `businessLineId,_id` 分页发现节点，不依赖售后头中可能遗漏的清单。保持当前每售后最多 100 节点的边界；超限或来源损坏报告失败，不截成完整。
4. 页是提示。在按 token/revision 比较的领取事务中，把有限页内节点加入持久“待确认”清单后才能前移队列发现位置。进程崩溃或中途预算耗尽，未处理节点仍在清单，不因扫描位置前移而丢失。
5. 业务新登记会换 token 并从起点重新发现；旧工作器最多重复计算，不能推进新代际、清除其清单或删除新工作项。claim/ack 的 revision 冲突保守停止，不能用无条件 set/remove 抹掉别人进度。
6. 每个实际发布仍走完整当前售后/节点/反馈/审核轮/票覆盖校验，在发布事务内固定读、重建完整结果并比较外部 sourceDigest/sourceHeader，再按原投影判断是否写快照。四候选预读仅非授权提示；不能跨事务复用当前资格。
7. 只有本代际已明确成功处理或权威确认不再适用的节点才能移出待确认清单；失败/未知不伪装成功。确认可按本次连续成功小批合并，必须记录真实操作成本。
8. 发现尾部且待确认清单为空后，才按 token/revision 条件删除该工作项。失败节点保留待恢复，不写原始错误正文；待确认重访和发现新节点的份额需有界轮换，避免一个持续坏节点饿死同售后的健康后继。已有完整巡检也提供独立公平性兜底。
9. 同一调用队列与巡检命中相同节点可用已完成的本调用结果省去重复恢复，但只可作为调度去重，不复用权限/来源事务读；若需要省略第二次恢复，必须证明没有跨过新的变更登记/来源读时点，否则保留两次。第一版可不做此去重，分别计入成本，不为追求指标放宽证明。

已失去资格或已删除的来源按当前恢复逻辑不发布。现有过期派生不因此直接批量删除；读取端继续凭当前节点/售后资格拒绝失效结果，保持现有语义。

## 完整巡检和状态推进

- 原完整来源算法保留；原 40/5 秒是合并阶段总上限，不变成“队列 40 再巡检 40”。完整巡检实际获得多少候选必须出现在测试计数中。
- 控制缺失首次进入新模式：通过 CAS 建立巡检代际并继续原游标，不擅自清空旧游标。原游标损坏仍失败关闭。
- 巡检完成必须同时有真实尾部证明、原游标对应已提交版本及当前控制代际；用固定文档事务确认，不能以旧工作器的 `hasMore=false` 或已回绕的 null 单独关闭新巡检。
- 控制完成写入把 nextRepairAt 设为有效服务端完成时间加 60 分钟；各节点页之间不更新 nextRepairAt。正在运行的巡检即使跨过该时间仍继续本代际，不为赶时间重开头部。
- 平台重入/冲突不能回退游标或关闭别人的巡检。允许重算不允许覆盖较新来源；未知提交停止本轮，不重放操作。
- 单条坏来源可记录安全失败并保留原公平推进；它不等于派生数据完整。长耗时 SDK 无法强行取消，因此 5 秒只是协作预算；必须测试边界并在发布前核对函数超时。
- 系统时钟回退不得使未到期状态提前运行或把 nextRepairAt 向过去改写；非法/过远未来/错误类型的状态须安全失败并可诊断，不能悄悄永久暂停修复。确切日期边界由计划显式列出并测试。

## 兼容与发布开关

本地候选保留两个明确服务端开关，默认兼容旧行为：API 是否写变更队列、worker 是否使用 priority-repair 模式。它们不是客户端参数，不接入任何 Secret；本轮不在线创建/修改环境变量。

上线顺序须在独立授权后执行：备份现网和配置、确认私有集合权限/索引、先部署带关闭开关的准确候选、开启 API 登记并短时保留旧巡检、核验登记、再开启新恢复模式并独立读回。过渡期额外队列成本计入，不宣称免费。具体配置版本数量、测试调用和云费用须在部署实施计划中列明并提前确认。

任一发布门禁不通过保持/恢复旧扫描模式，保留队列和备份，不删业务、快照、镜像或历史。回退只切本项开关/准确代码，不停原 Timer、不改业务/提醒。若环境能力需要新增 IAM、付费承诺、升级或其他访问范围，停止并明确告知；本设计不授权这些动作。

## 验证与成本门禁

先冻结当前全部相关运行源码和已有 dirty，再测试先行；不把旧计划测试绿当新设计通过。

- 十类动作、正常/失败/幂等重放；登记失败但同步刷新成功、同步刷新失败但队列存在、二者失败由完整巡检补齐；业务响应与通知不变。
- 首次启用、旧游标中段、空队列、全部不变、第一次巡检、巡检未完成续跑、漏标记及旁路同 ID/修订内容变化。
- 新变更与领取/发布/确认竞争、删除后重建 ABA、并发进程、SDK 冲突重试、未知提交已成功/未成功两种、冷启动和中途崩溃。
- 40/41/150/2000 节点、多售后热冷混合、100 节点边界、热点售后持续变更、坏队列/坏来源/低编号新项/高编号新项；健康后继最终可达。
- 反馈、轮次、投票、路线、资格变更；50 票上限和 100 操作事务预算；权限失效、普通账号拒绝导出；既有 CSV/客户端协议不变。
- 协作预算前后、时间回退、错误日历不污染字段结果；无新增真实发送、站内通知或业务写入。

相同夹具、完整 handler 的新旧对照：

- 0、30 完成、30 审核完成、150、2000 历史节点；单次变更、批量集中变化、持续变化、队列失败/恢复及全部未完成。
- 至少观察 1/10/100 次调用和完整 24 小时；虚拟间隔分别覆盖 1/5/15 分钟，但它们不是更改生产 Timer 的建议。明确暖机、首次完整巡检与稳定段，不只挑最省一轮。
- 逐集合、逐阶段计 get/query、实际返回文档、返回/写入 JSON 字节、set/update/remove、事务开始/重试/失败；业务变更登记与客户端原即时刷新都计入。
- 结果/快照、权限拒绝、原业务与站内/企微受保护集合保持一致；只允许新的队列/控制和原派生恢复状态变化。允许的统计恢复等待差异必须按本文件单列，不冒称逐时点后台结果完全相同。
- 原工时阶段同输入输出/扫描量保持，不把字段阶段节省用于扩大其任务量；已做的空游标复位不再次列收益。
- 先报告净 SDK/文档/字节/事务变化及摊销临界点。新增写入不能从成本表省略；费用换算需真实原始用量映射与同口径账单，未核实就写 unverified，不承诺固定元/月或整账单降幅。

本地门禁包括完整 Analytics、businessApi（含 pretest）、WXML、相关共享域同步检查、diff、项目记忆验证和新鲜独立复核。五端真机、真实 SDK/索引、云超时、最终现金是独立部署门禁，不用本地绿测替代。

## 交付顺序

1. 本文件已由独立构建者复核并获用户确认；当前仍只有设计，没有产品实现。
2. 确认后写实施计划，分成队列/接入、调度/完整修复、竞态与公平性、净成本对照、独立复核五个本地阶段。
