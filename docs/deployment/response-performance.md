## 范围与边界

本轮只优化既有流程：售后关系查询与候选重验有限并发、首页审核/通知单次受保护窗口统计、历史附件有限并发、检索代际写入与快照读取有限并发、计算内日历代际复用、上传预检同事务去重和客户端分段计时。

- 权限校验不跨请求缓存，不合并不同授权阶段的账号读取。
- 每组查询仍完整分页，候选仍重验后过滤、排序和分页；首页 2,000 条扫描边界与审核/通知 100 条窗口保持原含义，不把窗口计数称为全库总数。
- 并发池最多 4 项，结果保持输入顺序；失败后停止领取新项，并等待已经启动的任务结束后再向调用方报告失败。
- 检索内容及令牌全部写完才进入原发布事务；不去掉同步等待、不提前显示保存成功。来源版本、旧代竞争、幂等恢复与 100 次事务预算不放宽。
- 日历仅计算内复用，真正复用的代际在使用结果前复验；切换时有界重算，不同请求不共享缓存。
- 附件维持 3 文件并发、同对象短期授权刷新、真实大小/签名核验、120 MiB 合计和最终发布前重新授权。
- 不调整内存、超时、费用、密钥、权限、数据库索引或定时触发器；不靠写真实售后来压测。

审查发现的既有边界：保留期限已过、但仍为 `available` 且尚未实际清理的附件，其文件名可能仍参与当前快照索引；部署前备份也有相同行为。本轮不改变文件名元数据的检索保留语义，也不宣称它已按期限过滤。缺失、已清理、跨售后/节点及无效轮次附件的拒绝规则继续保留；文件本体访问与元数据检索应分开核验。

## 脱敏计时

客户端诊断默认关闭，无持久化、日志上传或新增后端接口。在开发者工具当前小程序 JavaScript Console 中可显式开启：

```javascript
getApp().globalData.performanceDiagnostics = true
```

执行正常界面操作后，只查看安全计时数组：

```javascript
getApp().globalData.performanceTimings
```

数组最多保留最近 100 条，只包含白名单 `action`、可选 `stage`、`durationMs` 和 `OK/ERROR`。不含正文、账号/售后/节点编号、文件名、路径、凭据或错误消息。上传阶段为 `authorize`、`transfer`、`finalize`；传输阶段包含内部网络退避/续期，最终核验过期重试可能生成两个 finalize 样本。云调用和上传阶段有重叠，不能简单把所有样本相加当作整页耗时。

关闭并清空：

```javascript
getApp().globalData.performanceDiagnostics = false
delete getApp().globalData.performanceTimings
```

不要输出整个 `globalData`、云响应或上传会话。跨设备比较使用同版本、同账号权限、同数据、相近网络；记录接口与整页渲染的区别。真实创建/审核/上传采用用户正常业务操作，不自动反复创建或提交测试售后。

## 当前测量证据

### 2026-10-09 创建与搜索调用计时补齐（部署状态见 STATUS）

本批仅补诊断，不改变初始化时机、实例缓存、数据库操作、一次性票据、权限、搜索并发或成功返回时机；它本身不是提速方案。没有新增依赖、配置项或定时器，也不需要小程序新包。日志只包含固定操作/阶段、毫秒数、状态及布尔值，不输出事件、返回正文、请求票据、记录/账号标识、密钥或异常详情。

| 日志 | 字段 | 含义 |
| --- | --- | --- |
| `[businessApi.creationTiming]` | `search_ticket_save` | 创建请求中签发并保存搜索票据的耗时 |
| 同上 | `search_function_call` | 等待 businessSearch 云调用及解包的耗时；它包含工作器运行、调度及传输等，不能直接当作网络耗时 |
| `[businessSearch.runtimeTiming]` | `handlerReused` | 请求进入时默认处理器是否已初始化成功；false 不等同于平台冷启动，初始化失败后的下一次尝试仍为 false |
| 同上 | `sdk_load` / `sdk_init` / `database_create` / `handler_create` | 首次处理器初始化中的 SDK 加载、初始化、数据库对象创建、仓储/服务/处理器装配 |
| 同上 | `handler_execute` | 实际处理器执行；正常索引请求内含已有的 `[businessSearch.indexTiming]` |

`runtimeTiming` 仅记录 index 调用，普通查询和 Timer 不增加该日志；若实例先处理过查询，后续首次 index 也会正确标记 handlerReused=true。复用实例不重做初始化，也不虚构四个初始化阶段的零耗时。计时上下文属于当前请求，客户端传入的同名字段不会用于计时或改变缓存。失败阶段仍记录 ERROR/失败标记，原有异常映射和创建成功但索引 pending 的行为保持；诊断时钟失效记录 null，不伪造零毫秒。日志写入异常被隔离，返回的 Promise 不等待，但同步日志/计时本身仍有少量开销，不能声称完全零开销。

解读时按平台请求分组，对应用户正常创建的时间窗口和关联的搜索调用；不要仅以接近的时间把并发请求误配。父阶段包含子阶段：API 的 search_sync 包含票据保存与搜索调用；runtime 的 handler_execute 包含 indexTiming；indexTiming 的发布阶段包含发布事务/读写。不可把这些父子数值重复相加，卡片刷新与搜索同步也有重叠。平台 Init Report 与 Duration 按平台口径分别核对，不能把剩余差额全部认定为冷启动。对比首次与复用样本用于定位，不据单样本承诺 1–3 秒。

未来经授权发布时，须重新核对准确线上基线并隔离其他未提交内容。本批 businessApi 涉及 lib/creation-timing.js、lib/business-service.js、lib/search-version.js、lib/business-search-client.js；businessSearch 涉及 index.js 和新增 lib/runtime-timing.js，**不能只发布 lib 而遗漏入口接线**。先后发布可兼容，无新增事件/返回载荷依赖；入口和新库文件必须一并核验，回下载确认后再用真实正常业务观察，不自动创建测试售后。发布、资源调整和 Git 提交需独立授权。
