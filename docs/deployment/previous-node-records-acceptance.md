# 前序节点记录验收

## 范围与发布

处理页、审核详情页的当前节点摘要下增加共享「前序节点记录 · 只读」折叠区。首次展开才读取实际流转列表，展开一个节点才读取最终结果；历史保存及各轮审核另行展开。只显示当前查看节点之前已完成的节点，不包括未走到的分支、当前节点或未来节点。

需要同时发布包含 `getPreviousNodeResult` 的 `businessApi` 和上传包含共享组件的新版客户端；本次开发不等于已发布。沿用已有集合与索引，不改业务记录、模板、投票操作权限、定时器、依赖或凭证保留期。

- `node_review_votes` 使用现有 `reviewRoundId / createdAt / _id` 索引。
- 无审核节点的凭证查询使用现有 `evidences.feedbackId / _id` 索引。
- 最终字段复用已有最终来源校验；审核节点使用不可变审核快照及该轮全部凭证引用，无审核节点使用最终完成反馈。
- 新接口要求当前账号仍可读取该售后的字段。全局列表权限不等于字段权限，不增加审批或修改历史的入口。
- 历史缺失信息明确占位；无法证明最终来源时显示失败与重试，不把草稿冒充最终结果。处理人姓名通过提交人编号与实例参与人快照对应；无法可靠确定时不展示内部账号编号或伪造姓名。旧版节点仍可查看其处理历史，不强行查询不存在的审核轮次。
- 原有权限控制的 `getEvidenceAccess` 决定图片、视频和 PDF 能否打开；过期/已清理凭证不恢复文件。

## 隔离验收步骤

1. 用无敏感数据的测试售后准备已完成前序节点、当前处理节点及至少一个未走分支。分别从待处理和待审核进入，检查顺序及排除范围。
2. 在当前页输入未保存字段、说明或审核意见；展开、切换、收起前序节点并查看附件，确认草稿不变。
3. 前序节点有多次保存、返工、多个审核人时，对照最终通过轮次：字段、处理说明、提交人/时间、凭证以及审核意见保持一致；展开历史可看到旧保存和全部审核轮次，超过五轮可加载更多。
4. 至少一张凭证来自最终处理轮较早的一次保存，验证仍在最终结果中。测试图片、视频、PDF，以及已过期/已清理的凭证。
5. 模拟断网、快速切换节点、收起时请求仍在途中、切换账号/停用账号，确认有重试提示且旧响应不回填其他节点或新账号，不自动执行审批。
6. 原有保存、上传、提交审核、通过/驳回和首页卡片流程作回归。

## 2026-09-23 交互优化补充（本地，尚未上传）

此增量仅改客户端，沿用已发布 1.2.6 对应的后端接口；不需要再次发布 businessApi。处理/审核页面仍共用一个组件，不增加集合、依赖、缓存层或权限。

- 历史处理记录和各轮审核分别按需加载，分别显示等待、失败和重试；某一类失败不能挡住另一类。审核下一页失败后，保留已有页并用同一游标重试。
- 每条处理记录、每轮审核默认只显示摘要，点开才渲染其字段/附件/意见。在当前已授权节点内折叠同一条记录不重复请求；收起整区、切换节点、页面隐藏和账号失效仍清空，再次打开必须重新走服务端校验。
- 按钮全宽，标题/箭头分栏；字段改为紧凑键值布局。附件名省略显示，查看/已过期等操作状态不挤成竖排，不改变原文件名或历史数据。
- 视频在固定弹层内展示，有打开中、取消、关闭及播放失败反馈。重点检查横屏、窄屏和桌面窗口中关闭按钮可达性、关闭后停止播放、迟到授权不能重新打开。
- “返回当前填写/审核”先收起历史，再滚动至原页面锚点；不刷新工作区、不清除未保存字段、上传队列或待提交审核意见。
- 五端均须实测上述交互，尤其微信原生视频层级、系统图片/PDF预览后的草稿保留；编译和模拟渲染不能作为五端已通过的依据。

### 首次读取耗时边界

本轮只读合成探针使用真实仓储配合 fake DB，不连接云端、不读取业务数据。0/6/40/94 个同反馈附件分别产生 20/32/66/132 次读取，均串行；对应 3/4/4/6 个事务，单事务最多 7/12/46/46 次操作，0 写入。这证明存在串行读取成本，但不是实际网络耗时，也不能证明录屏约 7 秒都耗在数据库。本轮不修改事务或削减权限/版本复核。

后续若继续优化首次加载，应先对同次只读请求对照客户端计时、云函数日志中的冷启动/执行耗时及数据库阶段耗时；仅记录请求追踪标识、阶段和耗时，不记录字段、文件地址、账号标识或其他业务正文。再判断是否对独立读取做有界并行；不能直接用缓存绕过当前授权。
